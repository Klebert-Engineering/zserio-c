## Statement of the rule (paraphrased)

Rule 19.2 (advisory): "The `union` keyword should not be used."

## Where it is deviated

In the C generated by `zserio_c.jar` for every zserio `choice` or
`union` schema type. The generator emits a tagged C union of the
form

```c
typedef struct ${typeName} {
    uint32_t tag;          /* or the schema's selector type */
    union {
        ${case0_type} field0;
        ${case1_type} field1;
        ...
    } u;
} ${typeName};
```

cppcheck flags every such union once on the `union { ... } u;`
line of the generated header. The runtime itself contains no
`union`; the deviation is generator-output-only and is enforced via
the `misra-c2012-19.2` suppression in
`tools/run_misra_generated.sh`'s CLI suppressions list (see the
comment block there for the full set).

## Justification

A tagged union is the natural C representation of zserio's `choice`
and `union` constructs:

- A `choice` selects between alternative payload layouts based on a
  parameter expression. The shapes are mutually exclusive — at most
  one is live at any time. A C union with a discriminator
  (the selector expression for `choice`; an explicit `tag` field for
  `union`) is the storage-efficient, type-checked representation of
  that "exactly one of these" semantics.
- The alternative — a `struct` with all arms always allocated — would
  waste memory linearly in the number of arms, and would force the
  caller to track validity per-arm through external bookkeeping. It
  would also disagree with the upstream C++ generator's variant-typed
  representation, breaking wire-level equivalence at the API boundary.

Rule 19.2 is **advisory**, not required. MISRA's stated rationale is
that union semantics can be implementation-defined when used to
re-interpret bit patterns of different types ("type punning"). The
generator uses the union strictly as a storage discriminator: each
arm is written and read only through its own member, and the active
member is determined by the explicit discriminator. The
type-punning hazard does not apply.

## Mitigation

- **The discriminator is always present.** The generator emits
  `case`/`tag` storage alongside the union and routes every read,
  write, observe-context, and free through a `switch` on it. There
  is no code path that accesses `u.fieldN` without first having gone
  through that switch.
- **No bit-pattern reinterpretation.** Each arm is read and written
  by its own typed accessor — there is no implementation-defined
  cross-arm read.
- **Strong end-to-end check.** Every choice/union generated by the
  toolchain is exercised in the `xvalidation` job, byte-equal
  against the upstream C++ generator's representation of the same
  schema, for every commit. A misuse of the union (writing one arm,
  reading another) would surface as a wire-format divergence.
