## Statement of the rule (paraphrased)

Rule 11.5 advises that a conversion should not be performed from a
pointer to `void` into a pointer to object.

cppcheck's MISRA addon also reports Rule 11.8 (cast removing
qualification) on the same construct as a secondary check. Both are
suppressed for the same call sites with the same rationale.

## Where it is deviated

Runtime call sites on the allocator vtable's `void *` boundary:

- `runtime/src/string.c:108` — `(char *)alloc->vtable->alloc(...)`
- `runtime/src/bytes.c:77`   — `(uint8_t *)alloc->vtable->alloc(...)`
- `runtime/src/extern.c:85`  — `(uint8_t *)alloc->vtable->alloc(...)`
- `runtime/src/allocator.c`  — `(zserio_arena_t *)userdata` inside
  the bump-arena callbacks. The cast is the inverse direction (the
  vtable's `userdata` field is `void *` so a single vtable can
  carry any allocator's state; the callback recovers the typed
  state on every call).
- `runtime/src/service.c`    — `(uint8_t *)alloc->vtable->alloc(...)`
  in `zserio_service_serialize` (the grow-and-retry serialization
  buffer for the generated service / pub-sub glue).

The vtable's `alloc` returns `void *` and its `userdata` is `void *`
to keep the allocator generic across element types **and** across
allocator implementations. Both directions of the cast convert
between `void *` and a target type immediately on assignment.

The **generator emits the same pattern** in every generated `_read`
that allocates an array or string. The call sites are
schema-dependent (one per allocating field per generated `.c`); they
share the identical justification and mitigation. Because the
file names vary per schema, the suppression for generator output is
applied in `tools/run_misra_generated.sh`'s CLI suppressions
(`--suppress=misra-c2012-11.5`) rather than as a path-scoped entry
in `tools/cppcheck-suppressions.txt`.

## Justification

The pattern is the standard C idiom for type-erased allocator
interfaces (it's exactly what `malloc` and `realloc` do, and what
every C library doing custom allocation does). Without it, the
allocator would have to be either:

- A template / generic in C, which C99 doesn't have, or
- A separate `alloc` callback per element type, which would explode
  the vtable surface from 3 entries to dozens, or
- Returning a tagged-union that the caller unpacks, which adds
  runtime overhead for no safety gain.

The cast does not introduce undefined behavior: `void *` can be
converted to any object-pointer type in C99 (6.3.2.3p1).

## Mitigation

- The cast appears in three well-defined call sites, each
  immediately following an `alloc()` whose `size` parameter is the
  allocation size of the target element type. The size and the
  target type are checked side-by-side in code review.
- The integer / pointer arithmetic that follows the cast in each
  call site is bounded by the allocation size.
- The allocator vtable itself is `static const`; the function
  pointers cannot be re-bound at runtime.
