## Statement of the rule (paraphrased)

Rule 21.3 prohibits the use of `<stdlib.h>` memory-management
functions (`malloc`, `calloc`, `realloc`, `free`, etc.).

## Where it is deviated

Three call sites, all in `runtime/src/allocator.c`:

- `allocator.c:32` — `malloc(size)` inside `libc_alloc`
- `allocator.c:43` — `realloc(ptr, new_size)` inside `libc_realloc`
- `allocator.c:51` — `free(ptr)` inside `libc_free`

No other source file in the runtime contains a direct call to any
of the prohibited functions. This is enforced by
`tools/run_misra.sh`'s forbidden-symbol grep (REQ-FS-001
verification), which would fail the build if a non-allocator file
introduced one.

## Justification

The runtime's memory model (REQ-FS-001) requires every allocation
to flow through the caller-supplied `zserio_allocator_t` vtable.
The `zserio_allocator_libc()` constructor returns a default-backend
allocator that wraps the C standard library functions; downstream
safety builds plug in pool / arena / static-buffer allocators that
have no relationship to `<stdlib.h>`.

The deviation is therefore strictly bounded: it exists in **one
file** that is the explicit, sanctioned wrapper. Removing the
wrapper would not make the code safer; it would just push the
malloc calls into application code outside the runtime's control.

The deviation does not apply to safety builds: those builds plug
in their own allocator and the `allocator.c` translation unit is
not linked, so `libc_alloc` / `libc_realloc` / `libc_free` are
absent.

## Mitigation

- The forbidden-symbol grep in `tools/run_misra.sh` runs on every
  CI build and fails if any file other than `allocator.c`
  introduces a libc-heap call.
- `tests/runtime/test_string.c`, `test_extern.c`, `test_bytes.c`
  exercise the allocator vtable through a counting tracking
  allocator and verify alloc/free balance, demonstrating that the
  vtable contract is honoured.
- Safety-build documentation will explicitly note that the
  `allocator.c` translation unit is to be excluded.
