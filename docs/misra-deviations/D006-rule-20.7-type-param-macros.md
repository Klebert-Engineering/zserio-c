## Statement of the rules (paraphrased)

Rule 20.7 requires that expressions resulting from the expansion of
macro parameters be enclosed in parentheses, to prevent operator
precedence surprises at the call site.

Rule 20.10 (advisory) discourages the use of the `##` token-pasting
and `#` stringification preprocessor operators because their results
are not subject to the usual semantic checks.

## Where it is deviated

- `runtime/src/varint.c:569` — `DELTA_TRAITS_UNSIGNED(SUF, T)`
- `runtime/src/varint.c:592` — `DELTA_TRAITS_SIGNED(SUF, T)`

Both macros take two parameters that are categorically *not*
expressions:

- `SUF` is a token-pasting suffix used only via `##` (e.g.
  `delta_read_##SUF`). Token-pasting operands cannot be parenthesised
  — `(SUF)` would prevent the paste and produce an invalid identifier.
- `T` is a type name used in declarations (`T v = 0;`) and casts
  (`(T)v`). The cast position already wraps `T` in parens, but the
  declaration position cannot: `(T) v = 0;` is a syntax error.

## Justification

Rule 20.7's intent — guarding against precedence bugs when a macro
parameter is interpolated into a larger expression — does not apply
when the parameter is exclusively a token-paste operand or a type
name. cppcheck's misra addon flags the macro definition lines without
analysing the parameter use sites, producing a categorical false
positive for this idiom.

Rule 20.10 forbids `##` token-pasting unconditionally. Token-pasting
is intrinsic to the idiom: nine varint flavours each generate four
distinct function symbols (`delta_read_##SUF`, `delta_write_##SUF`,
`delta_bitsize_##SUF`, `zserio_delta_traits_##SUF`), so the suffix
parameter must be pasted into the identifiers — no other mechanism
in C produces the same symbol names.

The alternative — hand-expanding the macros into 36 nearly identical
functions (9 varint flavours × 4 functions each) — would significantly
increase code size and review burden without improving safety. The
macros are self-contained at file scope of `varint.c` and exercised
by the `test_varint` and `test_delta` runtime tests plus the
xvalidation harness gate (REQ-FN-001), which together verify every
generated traits struct against the upstream cpp encoder.

## Mitigation

- The macros are file-scoped and end-of-file: no other code in the
  translation unit can interact with them.
- Every generated traits struct is exercised by the xvalidation suite
  (181/181 schemas × 5 seeds), which performs byte-equal round-trips
  against upstream zserio v2.18.1's cpp generator. A precedence
  surprise from a macro mis-expansion would manifest as a wire-format
  divergence in CI.
- The file-scoped suppressions in `tools/cppcheck-suppressions.txt`
  (`misra-c2012-20.7:*varint.c` and `misra-c2012-20.10:*varint.c`)
  apply only to `varint.c`; any new type-parameterised macro
  elsewhere would require its own deviation entry.
