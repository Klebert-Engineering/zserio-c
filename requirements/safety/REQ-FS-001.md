id: REQ-FS-001
title: No direct heap allocation
type: safety
status: accepted
verification: analysis
---

## Statement

The runtime library and any code generated by the zserio-c generator
SHALL NOT call `malloc`, `calloc`, `realloc`, `free`, `aligned_alloc`,
or any other function that allocates from the C standard library heap
directly. All dynamic allocation SHALL flow through the caller-supplied
`zserio_allocator_t` vtable passed to the corresponding API entry point.

## Rationale

ISO 26262 systems require that memory behavior be analyzable and bounded.
The standard C heap has implementation-defined behavior that varies by
toolchain, target, and load conditions. By forcing every allocation
through an explicit, caller-controlled vtable, we let safety builds plug
in a deterministic allocator (e.g. a fixed-size pool) and let test builds
use a tracking allocator that surfaces leaks and overflows immediately.

This is also the single largest reason the upstream C++ runtime is not
viable for ASIL production: STL containers grow under the hood through
their allocator template parameter, but in practice configuring a custom
allocator across an entire codec is impractical, so the default heap is
used. We avoid the problem by removing the direct heap call entirely.

## Verification

- A static analysis check (cppcheck rule, plus a `grep` linter in CI as a
  belt-and-braces backup) flags any direct call to the forbidden symbols
  in `runtime/` or in code emitted by the generator.
- Unit tests instantiate runtime objects with a counting allocator and
  assert that `alloc_count == free_count` at teardown for every test.

## Notes

- The forbidden-symbol list also includes any `_aligned_malloc`,
  `_aligned_free`, `valloc`, `posix_memalign`, `mmap`, `sbrk`, and
  `pvalloc` style escapes.
- The check applies to runtime and generated code only. Test scaffolding
  and host-side tools (e.g. coverage post-processors) are exempt.
